# Tracker 3.2 — качество сигналов (тестовая ветка)

**Статус:** исследовательский код в `tracker-v3.2-testing`, открытый Draft PR #1. Не сливать автоматически в `main`. Система не размещает ставки и не использует торговые ключи.

## Что изменено

1. **История кошелька.** Кроме доли прибыльно закрытых позиций (это НЕ точность предсказания), считаем суммарный плюс, суммарный минус, их отношение `profit_factor` и средний реализованный результат позиции. История ограничена последними `SAMPLE_CLOSED` позициями. Никакого «ROI» из этих данных не выводим.
2. **Слишком дорогой вход.** Сохранился фильтр BUY от $0.98. Дополнительно, при `COPY_QUALITY_GATE=1`, сравниваем цену покупки наблюдаемого трейдера с **доступным сейчас** $1 ask-side sweep. По умолчанию отклоняем сигнал, если средняя предполагаемая цена выросла более чем на 5¢ ИЛИ более чем на 20% относительно цены трейдера. Это эвристики, не доказанные оптимальные пороги.
3. **Признаки хеджирования.** Сигнал проходит как чистый BUY только при одной купленной стороне, публично подтверждённой позиции и отсутствии второй стороны в том же рынке. Любой пропуск API, неизвестный минимум $1 или невозможность оценить цену блокирует *копируемый BUY*, а не выдаёт ложную уверенность.
4. **Операции кошелька.** Отдельный read-only модуль выборочно смотрит 14 дней `SPLIT/MERGE/REDEEM` через публичный `/v2/activity`. MERGE/SPLIT — диагностический флажок, **не автоматический бан**. Один REDEEM обычно просто расчёт позиции. При неполной пагинации или ошибке никаких «чистых» выводов нет.
5. **Проверка нашей цены и результата.** `paper_v31` по-прежнему записывает виртуальный $1 BUY **только после успешно отправленного уведомления**. Теперь в записи также есть цена трейдера, наша предполагаемая цена и их разница. Исход и валовая виртуальная P&L считаются отдельно, после подтверждённого settlement. Оценка 1% friction — предположение, а не фактическая комиссия.
6. **Что пропущено.** В `suppressed_v32` остаются ограниченные по числу метаданные отфильтрованных BUY, причина и иногда известная quote; Telegram и бумажная позиция для них не создаются. Сбор статистики по наблюдаемым BUY fills начиная с момента мониторинга — не полная история кошелька.

## Запуск и ограничения

На **тестовой** ветке в `.github/workflows/tracker.yml` параметры `COPY_QUALITY_GATE=1` и `FORENSIC_SAMPLE_ENABLED=1` подготовлены для будущего контролируемого запуска. GitHub cron выполняет workflow **дефолтной ветки**, а не этой тестовой ветки; мы вручную tracker workflow не запускали. Запуск tracker workflow с Telegram-секретами может отправлять уведомления и менять тестовое состояние — не делать этого до отдельного согласования.

Проверка в PR выполняет офлайн-тесты и read-only smoke публичных API **без** Telegram, ставок, записи состояния или ключей. Полный жизненный цикл сигналов на большом будущем потоке пока не проверен. Положительный `profit_factor` и успешная проверка не доказывают прибыльность копирования: важны доступная цена, время, ликвидность, комиссии, качество исхода и selection bias.

**Следующий шаг:** собрать проспективные наблюдения, сравнить отфильтрованные и допущенные сигналы, оценить доступность входа, завершённые исходы и P&L после реалистичных издержек. Пороги менять только по заранее заданному тесту, а не подгонять по одному удачному дню.
