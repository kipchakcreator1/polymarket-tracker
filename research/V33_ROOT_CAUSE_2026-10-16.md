# Why v3.3 went quiet despite green tests — evidence and corrective work

**Date:** 2026-10-16 (US Pacific). **Project:** `kipchakcreator1/polymarket-tracker`. **Cost policy:** $0 / public read-only APIs / standard public GitHub Actions / no real orders.

## Verified production evidence

- [Session 38875939621](https://github.com/kipchakcreator1/polymarket-tracker/actions/runs/38875939621) is a ~50-minute real signal session after the short-crypto topic-only filter. It recorded 62 `V33 SUMMARY` lines, totaling **450** new wallet trade records and **1** verified BUY alert. The *per-poll veto deltas* sum to **270 off-topic**, **26 crypto markets too close to ending**, **3 crypto markets too far out**, **15 subthreshold**, and **14 mixed/SELL**; the counters are processing counts and not independent trading opportunities. This demonstrates a funnel with extremely little relevant input, not a dead Telegram integration.
- The selected wallet universe was a ranked sample of **250 general-market profitable accounts** from a 10,000-wallet universe; it did **not** measure their activity on BTC/ETH/SOL/XRP 5m or 15m markets.
- `tools/v33_wallet_universe.py` discovered wallets only through generic top/rotated Gamma `/markets` pages and incremented nonunique `mid_buys_sampled` across repeated queries. That built legacy popularity/activity rankings, not a crypto-focused list. At exactly `TARGET=10000`, `incorporate_sample` dropped all new wallets not already in the map. Combining that with a subsequent crypto-only signal filter was the primary mismatch.
- The 5-minute copy rule still requires a **recent source BUY (<=75s old)** and **>=90s remaining** in the market. These requirements are meant to avoid stale human-copy signals. Loosening them simply to increase counts would misrepresent copyability.
- Earlier code and workflow mistakes (default minimum $50 vs live $35, CI syntax mismatch, and occasional public API 429s) sometimes blocked runs; tests/green checks alone never showed end-to-end success.
- The GitHub Actions schedule is **best effort** and run-group concurrency can queue/cancel pending runs. Releasing workflow changes via a `push` can cause an immediate run, creating the illusion that messages only arrive after a user asks for a fix. The chat does not power the bot. Some sessions continuously scanned while sending zero; the wrong-wallet funnel was a major independent issue.
- Telegram `sendMessage` response `message_id` proves server acceptance, **not** push visibility on the user's device. `last_telegram_acceptance` is stored without Telegram chat/token.

## Implemented corrections

1. **Crypto round discovery:** `discover_short_crypto_markets` queries canonical Gamma event slugs for BTC, ETH, SOL and XRP 5m and 15m windows, 24 recent market rounds, not only the generic `/markets` feed. Lookups strictly validate slug and condition id. No fabricated rounds/markets on API failures.
2. **Source-time wallet relevance:** `fetch_market_trades` records recent qualified BUY activity in each sampled crypto round (midprice, $10 minimum source value) using the trade's real timestamp, preventing a reread from refreshing old evidence. This does not assert the BUY is profitable to copy.
3. **Live watchlist now favors active crypto:** `eligible_research_wallets` sorts wallets with a *real* last crypto BUY inside 24 hours above general winners, while preserving historical filters (>=30 closed positions, >=70% profitable closures, >=$100 realized profit, profit factor >=1.15, valid price profile). Live `select_wallets` still applies quality checks, and the specially requested wallet remains pinned when qualified.
4. **Prevent 10k hard freeze:** target temporarily increased to 12k and a bounded **max 100 per research run** eviction path admits new crypto activity even at capacity, only replacing stale generic unqualified candidates. Quality-validated and currently crypto-active entries cannot be evicted by this path. The replacement logic has specific offline regression tests.
5. **Less public API contention:** score 75 candidate histories per research run with two worker threads rather than 150 with five. Public API 429s are backed off instead of treated as wallet quality.
6. **Production honesty:** the live monitor logs `crypto_recent_watching` in `last_run`, checkpoints every confirmed BUY instead of only every third poll, and publishes per-run GitHub Actions job summary including recent qualified crypto coverage and failed polls. Multiple failed polls mark the job as failed rather than false-green.
7. **No fake trade inflation:** topic restriction, price/spread/book checks, duplicate prevention, recent/active risk gates and min BUY $35 are retained. No change to actual trades or wallet keys. Old v3.1/v3.2 automatic schedules stay paused.

## Still unresolved / acceptance criteria

- Confirm several fresh **genuine crypto BUY** Telegram message IDs, not health messages, after new wallet selection in production. A zero-signal hour *can be valid* if sources are not buyable/verified.
- Measure over a representative full day: relevant-wallet coverage, genuine BUY/24h, median and worst latency, active failures, and each filter's *per-poll* reasons. Avoid promises of every-minute BUY messages.
- Verify actual Telegram chat receiving messages separately; server acknowledgment does not guarantee the user's phone displays an alert.
- Wallet **general** closed-position winrate is not crypto-specific predictive edge; no prospective evidence of positive copied-trade P&L exists. Do not describe these wallets as profitable to copy without a friction-aware forward evaluation.
- GitHub's free scheduler and public APIs can be delayed, rate-limited or unavailable; $0 and hard uptime guarantees are incompatible without additional infrastructure. No paid infrastructure has been introduced.
